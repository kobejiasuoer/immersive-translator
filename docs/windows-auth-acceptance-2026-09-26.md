## 一、做了什么

按设计文档实现了 Windows 客户端的账号登录能力,分两侧:**Rust 侧**(新增 `src-tauri/src/auth.rs` 约 1740 行)负责全部登录相关的网络请求、令牌保管与刷新——令牌只存在 Rust 进程内与 Windows 用户级加密存储(DPAPI,按用户+机器加密)中,**前端界面拿不到令牌本体**,只拿到「已登录/未登录、用户资料、失效原因」;实现 8 个认证命令 + 3 个窗口命令并登记,登录状态变化时向所有窗口广播;应用启动时静默恢复登录(磁盘有凭据即显示已登录,联网后再校验存活);托盘菜单加「账号登录」项;`secret_store.rs` 加进程级写锁防并发丢数据;配置文件注册登录窗。**前端侧**新增登录窗界面(邮箱 → 6 位验证码 → 成功自动关窗;密码页签;60 秒重发倒计时关窗不丢;账号被封禁时阻断提交)、设置页「账号」标签(未登录空态 / 已登录资料展示 / 失效警示条 / 登出)与错误文案统一映射;配套 5 个测试文件共 63 个用例。

**关键产品决策**(设计定稿,这里只讲行为;设计评审 3 轮的过程记录见设计文档 §12,本报告不重复):

1. **登录是可选增强,不阻断任何现有功能**(D1):不登录,翻译/OCR/阅读室等照常可用;首启不弹登录窗。
2. **验证码为主入口、自动建号**(D3):未注册邮箱输入验证码即自动创建账号;密码页签服务已有密码的账号;不做注册/忘记密码入口(后置)。
3. **令牌永不进前端**(D4):界面与开发者工具里看不到令牌;本次评审还发现并修复了一个旁路(通用密钥读取命令曾能读出登录凭据,已封死,见 §4.2 #6)。
4. **失效提示不弹窗、不丢失**(D8):登录失效(过期/被强制下线)以持久警示条显示在账号页顶部,不自动弹登录窗打扰。
5. **重发倒计时关窗不丢**(D10):防止用户在服务端冷却期内反复点「获取验证码」却收不到邮件。
6. **单实例**:双开第二个实例会立即退出并唤起已有实例(防两进程共用同一令牌刷新被服务器判定异常、强制全部设备下线)。

**机制白话对照**(验收方无需理解实现术语,以下为行为含义):

| 实现术语 | 用户/产品视角的含义 |
|---|---|
| 单飞刷新 | 同一时刻只发一次「换新令牌」请求,并发场景共享结果。作用:界面各处同时需要令牌时不会重复请求;更重要的是防止「两个请求各拿同一张旧令牌去换新」被服务器判为凭据复用,导致该账号**全部设备被强制下线**(服务器红线,实测确认该行为,见 §三-0) |
| 代数清槽 / Shared future / 'static / manage 数量 | 均为 Rust 实现细节,作用是让上一条在并发下正确;已由编译通过 + 89 个单测背书,产品无需关注 |
| DPAPI 单槽存储 | 登录凭据以 Windows 用户级加密存本地;拷到别的机器解不开 |
| fire-and-forget 拉配置 | 登录成功立即返回(不等配置拉取),拉取在后台做、失败不影响登录;账号页有「重新拉取」按钮兜底 |

## 三、如何人工验收

### 前置

**1. 本地服务端**(API 在 8090 端口):

```bash
# 验活(当前已在运行;返回 401 unauthorized 即为活着)
curl -s http://127.0.0.1:8090/v1/me
# → {"error":{"code":"unauthorized","message":"缺少访问令牌"}}

# 若需自行启动(建议:由验收者自己起,验证码会打在这个终端上,见下)
cd D:/workspace/immersive-translator-server && pnpm dev
```

- **验证码不需要真实邮箱**:该服务器未配置 SMTP 时使用「控制台邮件」模式(已核实源码 `console-mail.sender.ts:12-17` 与实测行为——发码接口返回 `{ok:true}` 而非 503),验证码邮件全文(含 6 位码)打在**服务器控制台日志**里,形如 `[console-mail] 你的 immersive-translator 登录验证码 → xxx@test.local …你的登录验证码是 364882…`。当前运行中的服务器由工作流启动、控制台不在验收者手上,所以**建议验收者按上面命令自己重启服务端**以看到验证码;也可以用真实可收信邮箱代替。
- 限流注意:发码接口限每 IP 5 次/分、每邮箱 3 次/分(60 秒冷却),连续乱点会触发 429。

**2. 客户端**:

```bash
cd D:/workspace/immersive-translator/immersive-translator-windows
npm run dev
```

### 0. API 预检(纯 curl,约 2 分钟;以下命令与预期输出均由本报告 [复跑] 验证过)

作用:确认服务端行为符合预期,并顺手创建第 3 步「密码登录」所需的带密码账号(客户端无注册界面,验证码建号的账号没有密码)。

```bash
# ① 注册(密码至少 8 位;时间戳防重复)
curl -s -X POST http://127.0.0.1:8090/v1/auth/register -H "content-type: application/json" \
  -d '{"email":"acceptance-demo-<随便一组数字>@test.local","password":"Acceptance2026"}'
# → 201,返回 {"id","email","nickname":null,"plan":"free","createdAt"}   ← nickname 为 null 是真实形态,见 §4.2 #9

# ② 密码登录(拿令牌对)
curl -s -X POST http://127.0.0.1:8090/v1/auth/login -H "content-type: application/json" \
  -d '{"email":"<同上>","password":"Acceptance2026","device":{"platform":"windows","name":"ACCEPTANCE-PC"}}'
# → 200 {"accessToken":"...","refreshToken":"...","expiresIn":900,"user":{...}}

# ③ 带令牌读资料
curl -s http://127.0.0.1:8090/v1/me -H "authorization: Bearer <accessToken>"
# → 200 用户资料

# ④ 刷新轮换 → 旧票复用(复用会吊销该账号全部会话——这就是 §三-8 失效状态条的触发原理)
curl -s -X POST http://127.0.0.1:8090/v1/auth/refresh -H "content-type: application/json" -d '{"refreshToken":"<refreshToken>"}'
# → 200 新令牌对(旧刷新令牌立即作废)
curl -s -X POST http://127.0.0.1:8090/v1/auth/refresh -H "content-type: application/json" -d '{"refreshToken":"<旧refreshToken>"}'
# → 401 {"error":{"code":"token_reused","message":"检测到登录凭据复用，全部会话已吊销，请重新登录"}}
curl -s -X POST http://127.0.0.1:8090/v1/auth/refresh -H "content-type: application/json" -d '{"refreshToken":"<新refreshToken>"}'
# → 401 {"error":{"code":"token_invalid","message":"会话已失效，请重新登录"}}   ← 证明复用确实吊销了全部会话
```

(以上 6 步即本报告实际执行并拿到上述输出的链路,[复跑]。)

### 界面验收步骤(操作路径 → 预期现象)

> 注意:这是 **UI → 界面进程通信 → Rust → 本地服务器 完整链路的首次整体运行**(此前从未跑通,见 §4.1 第 1 条)。凡标注「待运行确认」的现象,其代码逻辑已读码核对但未经运行验证。

1. **验证码登录 happy path(判定 #1,唯一必验项)**
   路径:托盘图标右键 →「账号登录」(或 设置 →「账号」→「登录」按钮)→ 弹出 420×560 登录窗 → 输入邮箱(任意能收码的邮箱;若按前置说明自起了服务端,用 `me@test.local` 这类假邮箱即可,验证码看服务器控制台)→「获取验证码」→ 进入 6 位分格输入页,重发按钮 60 秒倒计时 → 填入验证码 →「登录」。
   预期:出现成功反馈,登录窗自动关闭;设置 →「账号」显示头像/昵称/邮箱/plan 徽标/当前设备/注册时间;侧栏「账号」状态点亮;**新邮箱的账号被自动创建**。登录后 Rust 会在后台自动拉取云端配置并落盘——**待运行确认**:检查文件 `%APPDATA%\com.immersivetranslator.windows\server_config.json` 是否生成(此自动链路此前无运行记录,见 §4.1 第 4 条;账号页「重新拉取」按钮为手动兜底)。

2. **验证码错码分支**
   路径:发码后输入错误 6 位码 →「登录」。
   预期:红条「验证码错误或已过期,请重新获取」,输入清空、焦点回输入格,重发按钮可用。(同一验证码最多试错 5 次,10 分钟有效——服务端规则。)

3. **密码登录(判定 #2)**
   路径:登录窗顶部页签 →「密码登录」→ 输入 §三-0 注册的账号邮箱+密码 →「登录」。
   预期:正确 → 成功反馈并自动关窗,账号页更新资料;错误 → 红条「邮箱或密码不正确;若从未设置密码,请改用验证码登录」。

4. **重发倒计时关窗不丢(D10)**
   路径:发码后倒计时未结束时直接关闭登录窗 → 重开登录窗输入同一邮箱。
   预期:「获取验证码」按钮仍禁用并显示剩余秒数(如「获取验证码(37s)」),归零恢复。**待运行确认**(代码已具备:守卫与按钮禁用均含剩余秒数,LoginView.tsx:115、274-275 [读码核对];该缺陷为评审发现 #8,修复后未经运行验证)。

5. **启动静默续登录**
   路径:保持登录态,完全退出应用后 `npm run dev` 重启。
   预期:不弹登录窗;设置 →「账号」直接显示已登录;后台自动续期无感。

6. **断网启动保留登录态 + 续期时机**
   路径:断网状态启动应用 → 打开设置 →「账号」→ 恢复网络。
   预期:断网时账号页仍显示已登录(本地凭据在即算已登录,离线不清);恢复网络后**无需重新登录**,登录态持续可用。
   续期机制说明(据设计 D6 与读码核对:auth.rs 中无任何定时器,仅启动时一次后台刷新):**没有网络探测或定时轮询**;续期由「下一次使用」驱动——任何需要令牌的操作(拉配置/拉资料/刷新按钮)发出前,若令牌剩余有效期不足 180 秒(或已过期)会先自动刷新再发。所以断网一天后恢复网络:登录态显示立即可用,下一次账号相关操作或重启应用时自动完成续期,全程无感;只有当刷新被服务器明确拒绝(失效/复用)才会转未登录。

7. **托盘双路径 + 已登录兜底卡 + 单实例**
   路径 a:未登录时点托盘「账号登录」→ 开登录窗;已登录时点 → 打开设置并定位「账号」页;设置窗已开着(隐藏)→ 即时切到账号页不重开窗。
   路径 b:已登录状态下再打开登录窗 → **待运行确认**:应显示「已登录」卡片(「打开账号设置」/「使用其他账号登录」两按钮),不重走登录流(LoginView.tsx:287-311 [读码核对])。
   路径 c:应用已运行时再启动一个实例 → 预期第二实例立即退出、已有实例的**设置窗**被弹到前台(lib.rs:1341-1345 [读码核对])。注:第二实例唤起的窗口目前固定为设置窗,这是产品交互决策点,见 §4.4 裁决事项 ④。

8. **登录失效警示条(判定 #4 的用户可见面;会吊销该账号全部会话,建议放在其他步骤之后做)**
   触发路径(全部 curl 均已 [复跑] 验证):让客户端处于登录态(账号 X)→ 用 curl 对**同一账号 X** 再做一次密码登录(拿第二组令牌)→ 用第二组的旧刷新令牌连续刷新两次(第一次成功轮换、第二次复用)→ 服务器吊销 X 的**全部**会话(含客户端持有的)→ 重启客户端(或点账号页「重新拉取」等需要令牌的操作)。
   预期:客户端变未登录,账号页顶部出现**持续显示的警示条**(本次演示得到的应是「登录已失效,请重新登录」;另一条文案「检测到登录凭据异常复用,该账号已在所有设备安全下线,请重新登录」为复用场景专用,两文案的前端渲染已由单测与原型覆盖,真机是否逐字呈现**待运行确认**)。警示条不弹窗、不自动打开登录窗;重新登录成功后消失。

9. **登出(判定 #6)**
   路径:重新登录后,设置 →「账号」→「登出」。
   预期:回到未登录空态卡+「登录」按钮;重启应用不再自动登录。
   登出失败分支的用户可见行为(据交付记录与设计,单测覆盖):**服务器侧吊销失败**(如断网)→ 用户照常登出成功、无任何失败提示(尽力而为,本地凭据已清);**本地清空失败**(存储异常)→ 保持登录态 + 红条「本地安全存储读写失败,请重试或反馈」,可重试,重试成功才真正登出。

10. **(可选)429 与封禁分支**
    429:界面上难以自然触发(按钮已被倒计时禁住);如需真实验证须绕过界面直接对发码接口连发(每 IP 5 次/分)。已由单测覆盖,可不做。
    封禁:需服务端预先封禁账号,不易构造;可跳过(前端单测已覆盖:红条「该账号已被封禁…」+ 提交禁用 +「返回修改邮箱」)。

### 4.3 契约与实现偏差(技术性说明,无产品影响的不展开)

1. 登出/轮换后旧访问令牌在最长 15 分钟内仍可读取账号资料——**这不是测试细节,是需要产品裁决的行为**,已提至 §4.4①。
2. 刷新令牌轮换与吊销的即时性只在「刷新」层:登出后旧**访问**令牌不复被本机使用(本地已清空),但服务器侧不立即拒绝它(同 ①)。
3. 若干纯技术偏差(命令返回类型包装、异步形式等):可观察行为与契约一致,编译与全部测试背书,不赘述;原始清单在交付材料中。

### 4.4 需产品/发布裁决的事项(建议在验收会上逐条定)

**① 登出后 15 分钟内旧访问令牌仍可读账号资料——接受还是改服务端?**
行为:服务器对资源接口(如 /v1/me)只验令牌签名与有效期,不查会话是否已被登出吊销;访问令牌寿命 900 秒,故登出/轮换后持有旧访问令牌者最长 15 分钟内仍能读取**账号资料与配置(只读)**——本报告 [复跑] 联调与 API 预检均受此约束(登出断言只能打在刷新接口上)。影响范围不含翻译通道(翻译走用户自配 Key,与账号无关)。
选项:A. 接受——短寿命令牌+刷新层吊销是业界常见做法,暴露窗口 ≤15 分钟且仅限只读资料;B. 要求服务端资源接口查会话(每请求加会话查询,或维护吊销黑名单),客户端无需改动。
**本报告建议:MVP 接受 A 并记录在案;若产品要求「登出即刻失效」,先排服务端改造。**

**② 5 条 low 级遗留的放行条件(§4.2 表中「仍在」项)**
建议:**带病放行**——5 条均为 low,触发条件苛刻或有自愈机制;其中 #1(http 明文配置)建议**发版前顺手修复**(改动小:校验地址必须 https 或本机回环),#2/#3 随下个迭代,#4 需先改设计契约、#5 归集成阶段补测。修复责任在开发侧,放行决策在产品侧;若产品要求「修完再发」,则 #1 为唯一必改项。

**③ 发布防呆机制**
现状:生产环境服务器地址依赖人工写一个配置文件,漏写则真实用户的登录全部打到本机开发地址而失败(发布清单只是 5 条人工步骤,§10,无机制防线)。
建议:增加机械防线——release 构建或启动时检测到「服务器地址为本机回环/开发缺省值」即告警或阻断登录入口,成本很小。**建议随 #1 一并在发版前落实,验收会上定。**

**④ 单实例:第二个实例该唤起哪个窗口?**
现状:第二实例唤起的是**设置窗**(lib.rs:1341-1345),而应用主界面是翻译面板(panel 窗)。未登录用户双击图标期望的可能是登录窗或主面板,直接弹设置窗未必符合预期。
建议:产品确认期望行为(主面板/登录窗/维持设置窗),改动成本约一行。
