# 移动端 App 调研（iOS / Android）—— 先想清楚，再动手

> 回答四个问题：手机端和桌面端怎么分工、第一版做哪些功能、用什么技术路线、联动（同步）怎么走。
> 上游文档：`docs/reading-room-handoff.md`（阅读室闭环）、`docs/reading-room-recall-brief.md`（产出式复习）。
> 结论不代表最终决定，供讨论。
>
> **2026-09-12 更新**：上架策略已拍板为**中国区首发**（本文 §6/§8 的「先上非中国区」结论过时）、开源策略已拍板为**客户端全开源 + 服务端闭源**（本文 §7 的推荐讨论均过时，最终结论以落地文档 §7 为准）、开发机已有 Mac。一切以 `docs/mobile-implementation-plan.md` 为准。

## 0. 一句话

手机端不是"桌面端的缩小版"，而是把阅读闭环里**碎片时间能做的部分**（复习、听、随手收集、轻阅读）装进口袋；桌面端继续承担深度阅读与整理。第一版聚焦"复习 + 生词本 + 轻阅读 + 收词"，登录和云同步放到第二阶段。

## 1. 现状盘点（决定了我们能复用什么）

| 资产 | 现状 | 对手机端的意义 |
|---|---|---|
| 技术栈 | Tauri 2 + React 19 + TS + Vite（Windows 端）；另有 `immersive-translator-mac`（原生 Swift） | Tauri 2 官方支持 iOS/Android；mac 端证明团队接受"多端各写实现、共享契约"的模式 |
| 数据契约 | `contracts/reading-room.schema.json` v1，`readerTypes.ts` 与 Rust `reader_store.rs` 同源 | 手机端照抄契约即可，数据模型零设计成本 |
| 存储 | Rust 侧存储，前端经 10 个 Tauri command 访问（`readerStore.ts`） | 命令面很小，跨端复写或复用都可行 |
| 数据模型 | `Article` / `SentencePair`（逐句 + 译文 + 词块标注）/ `VocabWord`（`kind: word \| chunk` + SRS 状态）/ `ReaderSettings` | 生词、词块、进度、设置全部有结构化模型，天生适合同步 |
| 纯逻辑模块 | `readerSrs` / `sentenceSplit` / `chunkAnnotate` / `dictCard` / `dictDetect` / `readerDict` / `articleBuilder` / `glossaryParser` / `languageDetect`，全部纯 TS + vitest 单测 | 手机端可直接复用（RN/WebView 均可跑 TS） |
| 翻译能力 | BYOK：deepseek / zhipu / dashscope / moonshot / openai / gemini / ollama，本地直连，无服务端 | 手机端同样 BYOK 可行；但移动用户填 key 门槛高（见 §6.4） |
| 复习闭环 | 收藏 → SRS 四档（10 分钟/1/3/7 天）→ 复习卡；recall brief 规划完形/听写卡 | 复习是手机端的第一主角 |
| 账号/云同步 | 无任何代码 | 是白纸，阶段二再设计 |

一个重要观察：**桌面端文章的 `SentencePair` 已经带译文和词块标注**——这意味着手机端即使完全不做翻译，只要把数据同步过去，"阅读 + 复习 + 听"的体验就是完整的。手机 MVP 可以零翻译成本起步。

## 2. 定位：手机和电脑各管什么

| 场景 | 桌面 | 手机 |
|---|---|---|
| 深度阅读长文、网页翻译 | 主力 | 不争 |
| 通勤/睡前轻阅读、听力 | 弱 | **主场**（锁屏播放、耳机线控） |
| 随手收集生词/句子 | 可以但慢 | **主场**（系统分享菜单，2 秒收词） |
| SRS 复习 | 已有，坐姿场景 | **主场**（排队/地铁 5 分钟一轮），频率预计高一个量级 |
| 批量管理、设置、整理 | 主力 | 只读/轻操作 |

与沉浸式翻译官方 App（内置浏览器 + 悬浮球 + Safari 扩展，全平台 2000 万用户）**不构成正面竞争**：它解决"译得快"（工具），我们解决"学得会"（生词 → 词块 → SRS → 产出式复习的学习闭环）。官方 App 没有生词本和复习，这正是我们的差异位。

## 3. 竞品手机端怎么做的

| 产品 | 平台 | 可借鉴的点 | 暴露的空位 |
|---|---|---|---|
| 蒙哥阅读器（Meerkat） | 仅 iOS | 点词即查（释义在底部，无需切 App）、生词在文中自动高亮、难度预标注、真人发音、iCloud 同步 | **没有安卓版**——国内安卓市场长期空缺，衍生出英阅阅读器、冰晶英文等平替 |
| LingQ | 全平台 | 复习五件套（卡片/反向/完形/听写/选择题）、内容市场、跨端同步 | 贵（订阅）、中文本地化差、界面老旧 |
| 沉浸式翻译官方 App | iOS/Android | 内置浏览器 + 悬浮球 + iOS Safari 扩展 + iOS 系统级"默认翻译 App"，体验完成度高 | 无学习闭环（生词/复习/统计） |
| 墨墨/不背单词（背单词类） | iOS/Android | SRS 的提醒推送、桌面小组件、打卡 streak 做得最好，是留存标杆 | 无"从阅读中来"的内容源 |
| Anki / Readlang / Migaku | 全平台 | cloze（挖空）是公认核心练习形态，与我们 recall brief 方向一致 | 移动端体验分散 |

启示：① 收集入口（分享菜单/导入）是手机端刚需；② 提醒推送 + 小组件是复习类产品留存的生命线；③ "原版阅读 + 生词管理"在手机端（尤其安卓）没有强势本土玩家，有空位。

## 4. 功能规划（P0 / P1 / P2）

### P0 —— 第一个能用的版本（目标：验证"碎片时间复习 + 收词"是否成立）

1. **生词本 + 词块本**：浏览/搜索/筛选；`kind: word | chunk` 分开计数（桌面端已有此概念），词块显示类型标签（搭配/短语动词/习语/句式）。
2. **SRS 复习**：四档评分卡先做识别卡；完形卡/听写卡的判分内核直接共享 recall brief 规划的 `recallJudge.ts`（纯函数），触屏打字输入反而比桌面更适合完形/听写。
3. **沉浸式阅读（移动版）**：读已同步的文章，双语对照、点词查词（tap 查词替代桌面 hover）、词块高亮、遮罩模式；**翻译为可选**（BYOK，可不填 key）。
4. **系统分享收词**：iOS Share Extension / Android 分享接收——在微信文章、浏览器里选中文字 → 分享 → 进 App 查词/收词/存为文章。这是手机端相对桌面最大的增量。
5. **联动 v0：文件互导**：桌面导出 contract JSON → 微信/AirDrop/局域网传到手机 → 一键导入。丑但能用，先用起来再上真同步。

**明确不做**：网页浏览器壳（不和官方 App 打）、OCR、口语打分、社区。

### P1 —— 留存与通勤场景

6. **听力通勤包**：后台/锁屏 TTS 连播、耳机线控（双击重播当前句）、倍速——逐句朗读机制桌面端已有，搬到移动端是体验重写不是逻辑重写。
7. **提醒与小组件**：SRS 到期本地通知（不需要推送服务）、"今日待复习 N"桌面小组件、打卡 streak。
8. **联动 v1：局域网直传**：桌面开端口出二维码，手机扫码全量同步（词表 + 进度 + 文章）。
9. **离线**：文章与词典结果缓存，地铁无网可读可复习。
10. **统计/打卡日历**：复习时长、新增生词、直译陷阱纠正率（recall brief 的独有指标）。

### P2 —— 登录之后

11. **账号**：手机号验证码（国内）+ Sign in with Apple（**App Store 硬性要求**：只要接了任何第三方登录就必须提供；且有账号必须能注销）。
12. **云同步 v2**：词表小 → 全量同步、按 id + 时间戳合并；文章大 → 摘要常同步、正文懒拉取；阅读进度取 max。
13. **商业化（如果做）**：订阅制 + 自家翻译代理（解决移动端 BYOK 填 key 体验差的根本问题）。
14. **AI 出新题 / 拍照取词 / 跟读打分**：recall brief 已推迟 ASR，维持推迟；OCR 桌面端有 `OcrOverlay` 先例，移动端可用系统级能力（iOS Vision / Android ML Kit）低成本实现，放观察项。

## 5. 手机端还能加什么（增量点子池）

按"性价比 = 对学习闭环的贡献 ÷ 实现成本"排序：

- **本地通知提醒**：SRS 到期 + 晚间固定时间提醒。成本最低、对留存贡献最大，没有理由不做。
- **小组件**：今日待复习数 / 每日一词。背单词类产品验证过的留存利器。
- **耳机线控翻页/重播**：通勤听书刚需，实现小。
- **系统分享收词**：见 P0-4，手机端的存在理由之一。
- **剪贴板检测**：复制了英文 → 顶部提示"查一下？"（可开关）。
- **锁屏播放卡片**：iOS/Android 媒体通知，听力模式的标配。
- **Siri 快捷指令 / Android 快捷磁贴**："开始今天的复习"一句话直达。
- **打卡日历 + 学习周报分享卡**：直译陷阱纠正率是独有数据，天然适合做传播。
- **键盘插件 / Apple Watch**：有意思但成本高，列观察项，不进任何里程碑。

## 6. 技术选型

### 6.1 推荐主线：Tauri 2 mobile

- 唯一能**同时复用 React UI + Rust 存储层（`reader_store.rs`）+ schema 契约**的路线；Tauri 2 自 2024-10 起正式支持 iOS/Android。
- 预计复用度：core 逻辑 100%、Rust 存储 100%、provider 调用 100%、阅读 UI ~70%（hover→tap、长按选词需触屏化改造）。
- 团队已有 Tauri 2（Windows）+ 原生 Swift（mac）双重经验，写自定义原生插件有基础。
- 已知短板：移动端 TTS 要自写插件（桌面 `tts.rs` 是 Windows 实现；iOS 用 AVSpeechSynthesizer、Android 用 TextToSpeech）；Share Extension / Widget 无论选什么框架都要写原生 Swift/Kotlin，跑不掉。

### 6.2 备选：Expo / React Native

- 复用全部纯 TS core 模块 + 契约；UI 全部重写（触屏本来也要重设计）；生态对 Widget、推送、分享扩展、后台音频最成熟，社区方案现成。
- 代价：`reader_store.rs` 的 10 个命令要用 SQLite/JS 重写（契约不变，风险可控）；UI 从零。
- **切换条件**：Tauri spike 发现 webview 体验不达标，或移动原生功能（分享/小组件）成为核心卖点而自写插件成本失控。

### 6.3 不推荐

- Flutter：Dart 重写一切，团队无 Dart 资产，core 单测资产作废。
- 双端原生：成本 ×2，仅 mac 端这种"契约已定、小功能面"的端适用。

### 6.4 API key 在手机上怎么办

- 阶段一维持 BYOK：key 存设备安全区（iOS Keychain / Android Keystore）。
- **但手机 MVP 建议走"零翻译"路线**：内容从桌面同步来（句子已带译文和词块），手机端先不填 key 也能完整使用；想翻译再加 key。移动用户单独注册 DeepSeek/OpenAI 的门槛远高于桌面。
- 阶段二登录后由自家服务代理，BYOK 痛点自然消解。

## 7. 联动方案（桌面 ↔ 手机）三步走

| 阶段 | 方案 | 成本 | 体验 |
|---|---|---|---|
| v0（P0） | contract JSON 文件导出/导入 | 极低（schema 现成） | 手动、丑，但数据无损 |
| v1（P1） | 局域网直传：桌面开端口出二维码，手机扫码同步 | 中 | 同一 Wi-Fi 下"一扫全同步" |
| v2（P2，登录后） | 云同步：词表全量 + LWW 合并，文章正文懒同步，进度取 max | 高（要后端） | 无感 |

登录体系设计要点（写代码前需再出独立 brief）：手机号验证码 + Apple 登录（硬性）+ 微信登录（国内安卓必要性高）；后端可用 Supabase 起步或自建；国内服务器需 ICP 备案。

## 8. 上架与合规（提前知道，避免返工）

- **iOS**：开发者账号 $99/年；接第三方登录必须同时提供 Sign in with Apple；有账号必须支持应用内注销；隐私政策必须；Share Extension 过审需演示真实用途。未上架前可 TestFlight 内测（90 天/轮）。
- **Android**：Google Play $25 一次性；**国内商店**需要软件著作权 + 工信部 App 备案（2023 起新规）+ 各商店逐个审核，周期数周——不急可先官网 APK / Google Play 分发，恰好安卓也是竞品空位。
- **支付**：iOS 虚拟商品必须走 IAP（抽成 30%，小型开发者计划 15%）。
- **隐私**：用户文本发给 LLM 供应商要在隐私政策明示。BYOK 个人工具风险低；若阶段二做自家代理服务，需评估生成式 AI 相关备案（使用国内已备案大模型 API 可显著降低）。

## 9. 建议的下一步（先不写代码）

1. **定 P0 范围**：建议最小闭环 = 生词本/词块本 + SRS 复习卡 + 读已同步文章 + 文件互导；分享收词看 spike 进度决定是否进 P0。
2. **交互原型**：按项目惯例做 `prototypes/mobile-v1.html`（单文件、四主题、`#demo=` 钩子），先把"复习卡触屏化"和"点词查词"两个关键交互定下来。
3. **技术 spike（两周内出结论）**：Tauri 2 iOS/Android 空壳 + 阅读页真机跑通 + 自写 TTS 插件验证 + 长文滚动性能。spike 结论决定主线还是切 RN。
4. **联动先做 v0 文件互导**，v1/v2 等使用数据说话。
5. **登录/云同步单独出 brief**，P0 验证后再写。

## 10. 开放问题（需要拍板）

- 目标用户设备占比：安卓用户多则"安卓先行（APK 分发）+ iOS 跟进"是合理路径，反之 iOS 先行。
- 桌面端 epub 导入尚未实现（`sourceType` 仅预留枚举）——手机端 P0 是否要补 epub 解析，还是沿用"粘贴/URL + 桌面同步"。
- 产品名与 App 图标（上架前必须定）。
