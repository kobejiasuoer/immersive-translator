# 沉浸阅读室 · 下一个核心需求方案：整本书阅读（书级载体）

- 日期：2026-09-23
- 作者：产品（需求综合）
- 输入：现状盘点、海外竞品调研（LingQ/Readlang/Migaku/Rebind 等）、中文与 AI 阅读产品调研（微信读书/薄荷/欧路/Kindle 等）、用户真实反馈（GH issues / Reddit / 应用商店）

## 1. 问题定义：用户正在用什么土办法硬扛

把输入四的真实痛点与输入二、三的竞品证据交叉验证后，痛点按强度排序如下：

| # | 痛点（一手证据） | 交叉验证 | 用户现在的土办法 |
|---|---|---|---|
| 1 | **整本书翻不动/翻完即坏**：EPUB 翻译导出损坏「翻译了十几本书，就这一本出了问题…calibre 无法打开」（GH#2430，同型 #2562/#2009，超 100MB 报错 #388）；长文档回看「段落会错位，找很久才能找到原来位置，我看的英文书籍成百上千页」（GH#59）；长页翻译整机卡顿（GH#1746） | 输入二：LingQ 六年花 $700+ 的重度用户最认可的就是「任意书籍导入」；输入三：微信读书/掌阅/欧路全部是「整本书 + 阅读器」形态 | 用 calibre 手工修损坏文件；把书拆成零散网页/文档分批喂给翻译工具 |
| 2 | **难书读不下去**：「一句话一半以上要查，我就把这本书放到一边」「碰到略高于水平的内容，要么跳过、要么抱着词典耗很久」（r/languagelearning 1tbqpxi）；薄荷付费用户「对英文原著产生恐惧，进行不下去」（szhome） | 输入二：Migaku 的「内容理解度评分」直接回答「这本书适不适合我」；输入三：Word Wise 仅覆盖部分英文书（Amazon 官方），用户仍缺难度透明 | 「超半句要查就换材料」的粗暴筛选法；或者苦熬 |
| 3 | **查了就忘、坚持不下来**：「同一个词要查三遍才记住」（r/languagelearning）；官方插件没有生词本，用户在 issue 里催「单词本的功能应该不难，为什么这么久都没计划？」（GH#3014）；用户自制 TTS 音频用 VLC 播放（1tbqpxi） | 输入三：Kindle Vocabulary Builder、欧路生词本验证「读到即收到、事后可复习」是留存核心；输入二：LingQ 被骂「复习太弱，被迫另配 Anki」 | A6 纸质笔记本自建页码索引「为了减少摩擦让我真的会用」（1tbqpxi）；VLC 播自制音频 |
| 4 | **每天读多少没数**：长书没有章节感和推进感，读没读、读多少全凭感觉 | 输入三：薄荷「打卡让我养成阅读习惯」被验证有效，但强制朋友圈打卡返现被骂惨（流利说差评、黑猫投诉） | 纯自律；或加入付费打卡营被套路 |

**关键洞察**：痛点 #3（查词→生词→复习链条断裂）恰恰是阅读室**已经解决**的部分——查词、生词本、SRS 复习、产出式复习流、快速复习窗、笔记库一应俱全。但这条闭环目前只能跑在**1650–4393 词的单篇短文**上（内置文库仅 6 篇，`core/library.ts:33`），而用户真正的诉求是「**读完并学会一整本英文书**」——链条的最上游（把整本书装进来、按章读完）是断的。土办法（calibre 修文件、纸质页码索引、VLC 播音频）全部是围绕「读完一本整书」的勉强支撑。

### 1.1 证据的产品线归属与「重合度」假设（诚实声明）

上表证据并非全部来自阅读室（桌面 Tauri 应用）用户，按产品线拆开归属：

| 证据 | 来源产品线 | 归属说明 |
|---|---|---|
| GH#2430/#2562/#2009/#388/#59/#1746/#3014 | 沉浸式翻译**浏览器插件** | 一手、可溯源，但是插件用户，非阅读室用户 |
| r/languagelearning 1tbqpxi、r/EnglishLearning「反复查同一个词」等 | 泛学习者社区（Reddit 等） | 与具体产品线无关，验证的是「读原文学词」人群的通用痛点 |

## 2. 用户与场景

**核心用户**（目标画像；「与现有阅读室用户重合」为待验证假设，见 §1.1）：

- **备考长跑者**（考研/四六级）：需要长时间消化大量语境，刷词表背不住（「背词表反效果，意义来自语境」，HN id7155941），要靠整本书阅读把大纲词「泡」进记忆。选书时关心「生词密度是否略高于我」。
- **原版书挑战者**：一年想读完 2–4 本英文书的人。过去用Kindle/微信读书读原版但查词后生词无处沉淀，或用沉浸式翻译插件翻 EPUB 但导出即坏。他们更可能要的是「读完 + 生词进复习」而非「翻译完拿到一个文件」（推断，非一手证据；证伪设计见 §4-D）。

**三个核心场景**：

1. **选书**：手上有一本想读的 EPUB（公版书/ purchased 电子书/ 自己收集的 .epub），导入前想知道「对我现在的词汇量，这本书读不读得下去」。
2. **按章精读**：每晚 20–40 分钟读 1–2 章。逐句对照、点词即查、查到的词顺手进生词本；读到哪记住哪，明天从断点继续——不需要「先翻译整本再读」，而是边读边翻，读完一章收一章。
3. **隔日回流**：昨天的生词到期，提醒卡拉回快速复习；复习完顺势打开书继续下一章。周而复始，直到这本书读完——书卡进度 100% 是产品能给的最强成就感时刻。

## 4. 候选需求与取舍

| 候选 | 判断 | 结论 |
|---|---|---|
| **A. 整本书阅读（书级载体）** | 痛点 #1 的唯一直解；missingLink（输入一）点名「epub/分章长书只有预留枚举，书架是平铺短文收藏夹」；且能放大既有复习闭环的全部投资——生词本/SRS/复习流/笔记库**一行不用重写**，只是数据源从「篇」变成「书的章」 | ✅ **核心需求** |
| B. AI 伴读划选追问（Rebind 式） | 有差异化且媒体口碑好，但不解决「土办法硬扛」级痛点；且现有词块标注（`core/chunkAnnotate.ts:22`）已承担「随读随注」的部分价值 | ❌ 本期不做，列为后续（见 §9） |
| C. 三级划选响应（Word Wise 内联短释义） | 好，但与书级载体正交；且句旁词块下划线 + 即时卡（ReaderApp.tsx:976-983）已是同思路的落地 | ❌ 不单独立项，并入书级载体的词块标注自然延伸 |
| D. 双语 EPUB 导出 | **显式假设而非结论**：痛点 #1 最硬的证据（GH#2430 系列）恰恰是「翻译完导出的 epub 损坏」——这批用户要的终端产物就是双语 epub 文件，拿它立项又拒绝做导出，必须给出可证伪的假设：「要导出双语文件的用户」与「愿意进入阅读室逐句精读的用户」是两群人（前者要的是插件产物，留在插件侧修复导出；后者要的是阅读行为本身——此为推断，无一手证据） | ❌ 本期不做；**证伪方式**：若阅读室书级留存/完书率（§8）长期低迷、而插件侧导出修复诉求持续高声量（GH 新增 issue 与商店评论声量），则两群人假设不成立，导出在阅读室重新立项；另 #2430 的直接根因「整本翻完再产出大文件」在阅读室架构下已被按章流式翻译结构性规避 |
| E. 轻量阅读营（定级+打卡） | 打卡有效性被验证，但社群形态被骂惨；缺「书」载体时打卡无对象 | ⚠️ 收窄为辅助增强二（产品内静默目标追踪，无社群） |
| F. 多引擎译文对照 / NotebookLM 音频导读 | 有趣但低频、不解决主痛点 | ❌ 后续候选池 |

**为什么不现在选 B/C 而选 A**：B、C 都是在「能舒服读完一篇短文」的前提下的增强；但现状是用户**连一本书都装不进来**（`core/readerTypes.ts:13` epub 仅预留枚举，导入四个 tab 无书籍格式）。容器不存在时打磨容器内的体验，边际收益低；A 是让既有六屏能力（阅读/查词/生词/复习/笔记/陪练）全部获得新场景的最短路径。

## 5. 核心需求详述：整本书阅读室

### 5.1 一句话定义

把「书」立为一等公民：**EPUB 导入 → 自动分章 → 按章精读（复用全部既有精读能力）→ 全书生词沉淀进既有复习闭环 → 书卡进度与章节推进**。读完一本英文书，从「不可能」变成产品的默认路径。

### 5.2 用户故事

1. 作为备考者，我把《The Call of the Wild》完整 EPUB 拖进导入窗，看到「7 章 · 约 32,000 词 · 约 4 小时」（章节/词数/估时来自解析实测口径，library.ts:21 的 135 wpm），以及选书雷达的「考研词表命中数千词 · 其中你生词本未掌握 M 个」与一句人话判定——我知道这本书「略高于我」，放心入库。（初稿示例「全书覆盖 214 词」与算法量级矛盾，已废弃；实测校准：用 examCoverage.ts:90-167 真实算法 + exam-wordlists.json 全表（考研 6,699 词）复算内置《野性的呼唤》第 1 章 3,715 词命中 751 词（node 实测，含 IRREGULAR_LEMMA 表），《The Devoted Friend》4,358 词命中 636 词——全书命中为数千词量级且随去重饱和亚线性增长，原型与 UI 中的数字必须来自导入时的真实计算，禁止写死。）
2. 作为读者，我打开书默认落在我上次读到的第 3 章第 14 句（断点续读升级为「书+章」两级）；朗读连播、点词查词、遮罩自测、手改译文——所有在短文上会用的能力一章内原样可用。
3. 作为学习者，我点查 "sledge" 后一键入生词本，词条来源显示「《野性的呼唤》· 第 3 章」；明天的复习流里这张完形卡带着原句书证来考我。
4. 作为读者，我读完一章，产品告诉我「本章查词 8 次 · 新增 5 词 · 用时 22 分钟」，我点「开始下一章」无缝续读。
5. 作为断续读者，我出差三天没读，提醒卡说「9 个词今天到期 · 你在第 4 章读到一半」，我点「继续阅读」直接回到断点。

### 5.3 关键流程

**流程一：导入一本书（导入向导）**

```
选择 .epub → 本地解析（zip + XHTML 抽取，Rust 端 or 前端 JSZip 管线）
  → 预览：封面/书名作者、章节树（章名+词数）、全书词数/估时、
         选书雷达（目标词表覆盖率 + 未掌握数，复用 examCoverage）
  → 用户可勾选章节范围（如只导 1–4 章）→ 确认
  → 逐章走 buildArticleFromText 建章文章（sourceType="epub"），书元信息入库

v1 分章规则（解析器的心脏，写死如下）：
  1) 以 toc.ncx / EPUB NAV 目录为准；一个 toc 条目可能对应多个 spine XHTML
     文件（「多 HTML 拼一章」很常见），按 toc 条目把它们合并为一章；
  2) 多级目录（卷/章/节）展平到叶子条目，卷名作章名前缀（「卷一 · 第 3 章」）；
  3) 无 toc、或 toc 条目对 spine 文件的覆盖率异常（如 <80% 的 spine 文件
     未被任何条目引用，判为可疑目录）时回退：按 spine 顺序每 ~3,000 词自动
     分节，命名「第 N 节」，预览页明示「未识别到目录，已按内容长度分节」；
     手动合并/拆分章节留作开放问题（§9），v1 只做提示不做编辑。
失败退路：DRM 加密 → 中文报错「该文件受 DRM 保护，无法解析」，不提供、
不暗示任何解除技术保护的指引（与 §9.5 版权红线一致）；一般解析失败 →
显示具体原因（格式损坏/无正文），引导重试或改走粘贴/文档导入，绝不产出
空书（与扫描件 PDF 同一口径，fileImport.ts:1-11 的先例）。
```

**流程二：按章精读（阅读页章节模式）**

```
书架书卡点「继续读」→ 打开断点章节的阅读页（句对主从版式不变）
  → 章内：逐句 TTS 连播 / 滚动跟随 / 点词查词典 / 加入生词本 / 遮罩自测
  → 章末句：弹「章末小结卡」→ 开始下一章（下一章内容懒加载；
    打开某章即整章后台串行翻译——与现有 ensureTranslated 行为一致，
    ReaderApp.tsx:503-580 对该章全部 pending 段落 for-await 遍历，
    「同一时刻一个请求在飞」；不做「只翻前 N 句」，那需要对触发时机
    动刀，v1 放弃）
  → 随时章节下拉跳章；书级进度条 = 已读章/总章 + 当前章内百分比聚合

翻译成本量级（估算口径）：buildParagraphTranslateSystemPrompt
（paragraphTranslate.ts:83）系统提示 ≈150 token/请求；一章 ≈4,000 词、
按段均 100 词 ≈40 个段落请求，每请求（系统 + 输入 + 输出）≈400–500
token → 约 1.6–2 万 token/章；7 章整本 ≈12–15 万 token（按需付：只翻
打开过的章，未打开的章零消耗）。此为估算，需在埋点（§8）里带
翻译请求计数验证。
```

**流程三：生词闭环与隔日回流**

```
查词入生词本（source=chapterArticleId+sentenceIdx，VocabSource 结构零改动）
```

## 6. 辅助增强一：选书雷达（难度透明）

**痛点**：「碰到略高于水平的内容，要么跳过、要么抱着词典耗很久」（1tbqpxi）；Migaku 靠理解度评分回答「这本书适不适合我」成为续费理由（immit.co）。

**做法**：导入预览页与书卡上展示三件套——① 目标词表覆盖率（考研/四六级，复用 `examCoverage.ts`）；② **未掌握词密度**（命中 ∩ 生词本未掌握，与文库「你生词本里未掌握」高亮同一口径，ImportDialog.tsx:195-301 已有先例）；③ 预计净读时 + 每章估时。给出一句人话判定：「略高于你的水平 · 适合精读」/「偏易 · 适合泛读冲刺」。

**为什么值得**：零 LLM 成本（纯本地词表交集），直接接在书级载体的导入流程上，且把「生词本数据」反哺到「选什么书」——闭环里第一次让复习数据影响上游决策。

## 7. 辅助增强二：章节进度 + 每日阅读目标追踪

**痛点**：薄荷验证「每日目标+连续天数」有效（「打卡让我养成阅读习惯」），但强制朋友圈打卡被骂惨；阅读室 `readGoalMin` 只存不追踪（`src/lib/reminder.ts:17-18`、决定记录 #16）、`secondsListened` 字段闲置（仅初始化写入 articleBuilder.ts:26，无其他写入点）。

**做法**：① 阅读页计时（朗读播放 + 阅读视口活跃均计入，写回章与书的 `secondsListened`）；② TodayCard（`src/reader/TodayCard.tsx:20`）增加「今日已读 X/Y 分钟」环，连续阅读天数与复习打卡并列；③ 提醒卡双态：有到期词 →「N 个词到期」；无到期词但未达目标 →「还差 M 分钟达成今日阅读目标 · 继续读《书名》第 N 章」。**不碰社群、不碰分享、不碰返现**。

**为什么值得**：坚持问题的一半是「没有可感知的推进」——章节进度（读完 3/7 章）+ 每日分钟数给了双重推进感，且全部复用提醒/托盘/TodayCard 已有触点，纯增量字段。

## 9. 风险与开放问题

**风险**

1. **历史决定冲突**：`docs/next-requirements-2026-09-15.md:44`（R1「不做 epub」）与 `product-audit-report-2026-09-15.md:350`（原文为「明确不做**（本期）**：……epub……」——旧口径带「本期」限定，本就是当轮范围裁剪而非永久决定，这对重新立项反而更有利）曾两轮搁置 epub。当时背景是「导入麻烦（P0）」优先救 docx/pdf，且无书级载体规划；本方案是在复习闭环已建成、missingLink 明确（输入一）、插件侧高频差评（#2430 系列——**注意其为插件用户证据，向阅读室用户的迁移性是 §1.1 的待验证假设**）三重新证据下的**重新立项而非翻烧饼**——评审需显式更新旧口径，避免团队认知混乱。
2. **epub 长尾解析质量**：市面 epub 结构千奇百怪（嵌套目录、脚注、多 HTML 文件拼一章）。缓解：只抽正文+章序（v1 分章规则见 §5.3 流程一），解析失败即显式报错绝不产空书；上线前用 Standard Ebooks 全本样本 + 20 本**自行整理的授权/公版杂源** epub（刻意挑嵌套目录、脚注、多 HTML 拼章的坏结构样本）建立回归样本集——不含任何来源不明文件（与风险 5 的版权红线一致）。
3. **大书 I/O 与翻译成本**：章=独立 Article 只是**逻辑**分片——存储层全部章仍落同一个 `reader_articles.json`，且该文件整文件读/整文件写（现状核实见 §5.5「存储改造」行），书多后流式翻译期间每 700ms 防抖一次的全量重写会重写几十 MB 级文件，「逻辑分章」「懒加载章摘要」在现有存储层都不成立。缓解（必做前置）：§5.5 存储改造二选一落地后书级化才开工；翻译严格按章按段串行（复用 ReaderApp.tsx:503-580 管线，同一时刻一个请求在飞），每章 token 成本估算见 §5.3 流程二。
4. **章节句号与生词定位稳定性**：章=Article 意味着句 idx 是章内局部序号，复习卡「原句定位」要带 bookId+chapterIdx 才能跳转回书内——跳转路由需要设计，先支持「跳到章首+句号定位」的降级版；书被删除后来源悬挂的降级契约见 §5.5「删除书契约」行（保留生词、降级为纯文本书证、不回跳）。
5. **版权边界**：产品只做「用户自带文件解析」，不内置任何非公版书源，产品内不出现任何解除 DRM/技术保护的指引（§5.3 流程一的失败文案已按此收紧）；内置文库仍限于 Standard Ebooks 公版（library.ts:1-7 口径不变）。

**开放问题**

1. Book 层契约放 `reading-room.schema.json` 的 schemaVersion 2 还是 v1 加可选字段？（倾向后者：`bookId?` 可选字段对老数据零破坏，与 `kind?: VocabKind` 的先例一致，readerTypes.ts:123）
2. 提醒卡的「继续阅读」如何跨窗口直达主窗断点章？（可复用 `takePendingReaderImport` 的 pending payload 模式，ReaderApp.tsx:743-800，待技术评审）
3. 「章」粒度：无章节结构 epub 的回退已定（§5.3 流程一规则 3：按 spine 顺序每 ~3,000 词分节）；仍开放的是**用户手动合并/拆分分节**要不要进 v1？（倾向不做，先观察回退触发率埋点 `book_import_result.failReason="no-toc"`）
4. 选书雷达是否引入真正的 lemmatizer（现在 examCoverage.ts:90-124 是规则屈折回落）以提升覆盖率精度？（v1 不引入，保持零依赖）
